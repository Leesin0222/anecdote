# Security Policy

We take security seriously and appreciate responsible disclosure. This page
describes which versions of `anecdote` receive security updates and how to
report a vulnerability you've found.

## Supported versions

Only the latest minor release receives security fixes. While `anecdote` is
pre-1.0, we will patch the most recent release on the `main` branch and ship
a follow-up version; we do not back-port to older `0.x` lines.

| Version    | Supported          |
|------------|--------------------|
| 0.1.x      | ✅ active          |
| < 0.1.0    | ❌ not supported   |

Once `1.0` ships, this table will be updated with a clear support window.

## Reporting a vulnerability

**Please do not open a public GitHub issue for security problems.** Public
issues are indexed and notified immediately, which can put users at risk
before a fix is available.

Use **GitHub Security Advisories** instead:

1. Go to
   [https://github.com/Leesin0222/anecdote/security/advisories/new](https://github.com/Leesin0222/anecdote/security/advisories/new).
2. Fill in a description of the issue. Include:
   - What kind of vulnerability it is (e.g. data leakage, dependency CVE,
     incorrect probe behavior that bypasses detection, mis-handled
     PII in reporters).
   - The version(s) affected (`0.1.0`, `0.1.1`, …) and the module
     (`anecdote-core`, an adapter, a reporter).
   - Steps to reproduce, or a minimal proof of concept if you have one.
   - The impact you observed and any suggested mitigation.
3. Submit. GitHub will notify the maintainers privately. You and the
   maintainers can then discuss in the advisory thread without the report
   being public.

If GitHub Security Advisories are not accessible for some reason, open a
[GitHub Discussion](https://github.com/Leesin0222/anecdote/discussions)
asking maintainers to contact you privately — **do not** include the
vulnerability details in the discussion itself.

## What to expect

- **Acknowledgement** within roughly one week of the report.
- **Initial assessment** (whether we can reproduce it and the severity we
  assign) within two weeks.
- **Fix timeline**: depends on severity. For a confirmed high-severity issue
  we will aim to ship a patch release in the next available release window;
  for low-severity issues we may roll the fix into the next regular release.
- **Coordinated disclosure**: once a fix is released, we will publish the
  advisory with credit to the reporter (unless you'd prefer to remain
  anonymous).

## What's in scope

The codebase in this repository:

- `anecdote-core` and any first-party `anecdote-adapter-*` /
  `anecdote-reporter-*` module under this repo.
- The `sample` app *only* if a vulnerability is reproducible against the
  SDK itself, not against the sample's own UI code.
- The build scripts, Gradle convention plugins, and CI workflows under
  `build-logic/` and `.github/`.

## What's out of scope

- **Bugs that are merely incorrect detections** (false positives or false
  negatives in `BlockState`). These are normal bugs — please use the
  bug report issue template for those.
- **Vulnerabilities in third-party SDKs** integrated via adapters (e.g. a
  CVE in Google Mobile Ads itself). Please report those upstream.
- **Issues that require a malicious app to already be running with root /
  full debugging access on the device.**
- **Reports generated by automated scanners with no manual verification.**
  We'll still look at them but they are usually low priority.

## Hall of fame

We are happy to credit reporters in advisory notes and the changelog unless
you ask us not to. Thanks for taking the time to make `anecdote` safer.
